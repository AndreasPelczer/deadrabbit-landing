iMOPS

Reference Kernel for Operational Documentation

OS_CORE v1.0.0

What iMOPS Is

iMOPS is a deterministic in-memory kernel for the digital documentation of operational measures in high-pressure environments. Born from 36 years of experience in professional kitchens and production management.

The system captures professional actions as chronologically ordered events, stores them traceably in a MUMPS-inspired storage model, and makes them available in a structured way for evaluation, auditing, and sharing.

iMOPS is not a framework. Not a library. It is a complete, self-contained system kernel with an integrated protection stack that travels with every fork.

What iMOPS Deliberately Is Not

iMOPS is not a decision-making system. It does not make evaluations, does not define thresholds, and does not replace professional concepts. Responsibility for content and procedures lies with the respective organization.

  • No cloud sync, no network layer, no login system
  • No CoreData, no CloudKit, no external database
  • No analytics, no tracking, no telemetry
  • No substitute for HACCP concepts, standards, or legal requirements

These are not missing features. These are design decisions.

Design Principles

Zero Dependencies

No Pods. No Packages. No external frameworks. Everything iMOPS needs lives within the kernel.

Offline-First

In-memory storage on Serial Queue. No server, no account, no connection required.

Deterministic Where It Matters

Storage, lifecycle, and export are deterministic. Where it protects people, deliberate noise is built in.

Guard Stack Travels With Fork

Whoever forks iMOPS inherits the complete protection stack. The kernel is only complete with its guards.

The Guard Stack (Gen 3)

iMOPS contains an integrated protection stack that shields people from micro-tracking, fatigue, and management abuse. The guards are not features — they are the ethical foundation of the system.

SecurityLevel

Exactly two states: standard and deEscalation. In de-escalation mode, all personal data is anonymized. There is no third level. Codable. CaseIterable. Tested.

A test explicitly prohibits adding a third level. Any change to SecurityLevel = v2.0.

MenschMeierModus

Anti-tracking protection via Rio Reiser Jitter: every aggregated stress value is offset with ±5% random noise. No value is exactly reproducible. Employees become patterns, not data points.

Anonymization: In deEscalation mode, every name is replaced by "Brigade" (Poison Pill).
Privacy Shield: After more than 50 admin queries, automatic escalation occurs.
Allergen Transparency: Allergen tasks are always visible, even when Privacy Shield is active. Obscuring data must never endanger human lives.

BourdainGuard

Fatigue protection with two fixed thresholds: 8 hours (warning with whisper message) and 10 hours (forced training mode). After 8h the jitter factor increases progressively (0.05 → 0.10 → 0.15), so that data becomes deliberately fuzzier during overtiredness.

Whisper messages are human sentences, not system alerts. "You've been here for 8 hours. Your team can manage without you." The 8h/10h thresholds are immutable — any change = v2.0.

KernelGuards

Single entry point for all guards. Combines SecurityLevel, MenschMeierModus, and BourdainGuard into a single GuardReport with jitterApplied, privacyShieldActive, fatigueLevel, anonymizedTasks, and whisperMessage.

One function: evaluate(). One report. No guard runs in isolation.

GDPR Art. 25 — Privacy by Design

Data protection is not an afterthought filter. It is built into every layer of the kernel.

  • HACCP archive stores roles, not names
  • Timestamps in hour windows, not milliseconds
  • Jitter prevents exact reconstruction of individual performance data
  • Privacy Shield escalates automatically on suspicious admin behavior
  • Export functions apply guards before data leaves the system
  • Anonymization takes effect system-wide — not just in the UI

prepareExport() checks SecurityLevel and Privacy Shield. No data record leaves the kernel without guard verification.

Self-Check & Integrity

On every system startup, the kernel performs a 13-step self-check. The result is immutably sealed in the HACCP archive.

01Validate namespace structure 02Check TheBrain Serial Queue 03SecurityLevel integrity (exactly 2 cases) 04MenschMeierModus jitter function active 05Privacy Shield threshold correct (50) 06Validate BourdainGuard 8h/10h thresholds 07Check allergen transparency 08KernelGuards orchestrator reachable 09Export guards active (prepareExport) 10Check archive format (role, not name) 11Time window granularity (hours, not ms) 12Task lifecycle integrity (4 stages) 13Seal boot result in archive

22 integrity tests additionally secure the guard stack. Including tamper detection tests that deliberately attempt to bypass guards.

Export & Audit

Three formats. All SHA-256 sealed. All guard-verified.

Daily Report

Structured text report with time period, documentation mode, and integrity status.

Audit CSV

Tabular format for inspectors and auditors. Roles instead of names. Hour windows instead of timestamps.

Journal JSON

Machine-readable for integration into external systems and archiving.

Integrity

SHA-256 hash via CryptoKit. Every export is retroactively verifiable.

What v2.0 Would Mean

  • Change of storage model (away from [String: Any])
  • A third SecurityLevel
  • Shifting the BourdainGuard thresholds (8h/10h)
  • Change of the HACCP archive structure
  • Introduction of mandatory dependencies

As long as these boundaries hold, every fork remains compatible.

Guard Integrity Is Mandatory

The guard stack is not an optional feature. It is the ethical foundation. Whoever forks iMOPS accepts the following rules:

  • KernelGuards.swift must not be modified
  • SecurityLevel remains at exactly two states
  • BourdainGuard thresholds (8h/10h) remain unchanged
  • Export functions and their GDPR guards are final
  • No personal data in the archive (roles, not names)
  • All 22 tests must pass. No exceptions.
Philosophy: The guard system protects people from micro-tracking, fatigue, and management abuse. A vulnerability in the guards is not a bug — it is a breach of trust.

Continuous Integration

GitHub Actions checks on every push and pull request to main: Build + all 22 Guard Integrity Tests. If a test fails, there is no merge and no deploy.

Security vulnerabilities in the guard system are not reported publicly. Contact: a.pelczer@gmail.com with subject [iMOPS SECURITY].

Audit Relevance & Scope

This information is intended for inspectors, auditors, and quality managers.

  • All manual actions are journaled as events
  • Automated system actions are separately marked
  • Documentation periods can be sealed and closed
  • Closed periods cannot be modified retroactively
  • Integrity can be verified at any time through integrated checks
  • Every action is attributed to a person or the system

Measures can optionally be annotated with professional references — internal process instructions, standard references, HACCP, ISO, internal SOPs. These references serve for classification, not for evaluation.

Anyone can read the guard code. Anyone can run the tests. Anyone can verify that the protection promises are in the code — not just in a marketing text.
